# StoryRest 구조 설계

> 요구사항은 `PROJECT_SPEC.md`. 이 문서는 그것을 어떤 구조로 구현할지를 정한다.
> 작성: 2026-08-05

---

## 0. 이 설계가 푸는 문제

기존 `ArUcoPages` 패키지는 **"카메라 영상을 화면에 띄우고 그 위에 이미지를 얹는"** 구조다.
카메라가 본 것을 사람이 모니터로 보는 상황이라 카메라 화각 = 출력 화각이 성립한다.

본 프로젝트는 다르다. **프로젝터가 실제 책자 위에 빛을 쏜다.**
관람객이 보는 것은 화면 속 영상이 아니라 종이 위에 겹쳐진 빛이다. 그래서

- **카메라 영상을 투사하면 안 된다.** 실물이 이미 거기 있다. 검은 배경 위에 콘텐츠만 쏜다.
- **카메라 픽셀 좌표를 그대로 출력 좌표로 쓸 수 없다.** 카메라와 프로젝터는 위치도
  렌즈도 다르다. 같은 각도로 달아도 수 cm ~ 수십 픽셀이 어긋난다.

두 번째가 이 설계의 핵심이다. 마커별 오프셋으로는 못 고친다 —
마커를 책상 반대편으로 옮기면 오차가 다시 벌어지기 때문이다.
**카메라 평면과 프로젝터 평면 사이의 호모그래피를 한 번 구해두는 것**이 정답이다.

## 1. 좌표계

좌표는 세 단계를 거친다.

```
  ① 마커 평면          ② 카메라 픽셀            ③ 프로젝터 픽셀
  (마커 한 변 = 1)  →  (검출된 네 꼭짓점)   →  (실제로 빛이 나가는 자리)
       H_marker              H_camproj
```

| 변환 | 얻는 방법 | 언제 정하나 |
|---|---|---|
| ① → ② `H_marker` | 마커 네 꼭짓점 → 단위 정사각형 (기존 `ArUcoHomography`) | **매 프레임** |
| ② → ③ `H_camproj` | 카메라-프로젝터 4점 캘리브레이션 | **설치 시 1회**, 파일로 저장 |

기존 코드에는 ②→③이 없다. "카메라 프레임을 화면에 레터박스로 맞춘다"가 그 자리를 대신하고 있는데,
그건 두 화각이 같을 때만 맞는 특수해다. 이 자리에 진짜 호모그래피를 넣는 것이 변경의 골자다.

### 무엇을 구하는 것인가

카메라와 프로젝터는 위치도 렌즈도 다른 별개의 장치다. 나란히 달아도 좌표계가 일치하지 않는다.

```
        [카메라]  [프로젝터]
           \        /
            \      /
        ─────●────────────   책상 위 한 점
```

카메라는 "마커가 영상의 (640,360)에 있다"고 알려주지만,
**그 자리에 빛을 보내려면 프로젝터의 몇 번 픽셀을 켜야 하는지**는 알려주지 않는다.
그 환산표가 `H_camproj`다.

책상이 **평면**이므로 평면↔평면 변환은 자유도 8, 즉 **대응점 4쌍이면 완전히 결정된다.**
한 번 구해두면 장비를 물리적으로 건드리기 전까지 유효하다.

### 4쌍을 얻는 방법 — 투사 마커 자동 인식(기본)

**프로젝터가 네 귀퉁이에 ArUco 마커를 직접 투사하고, 그 빛으로 그려진 마커를 카메라가 읽는다.**

- 프로젝터 좌표: 우리가 그린 위치이므로 이미 안다.
- 카메라 좌표: 투사된 마커를 검출해 얻는다.
- **사람의 개입 없이 4쌍이 즉시 완성된다.** 버튼 한 번으로 끝난다.
- 마커가 미세하게 떨리므로 여러 프레임(기본 30)을 모아 평균낸다.

캘리브레이션 전용 마커 ID는 콘텐츠와 겹치지 않게 예약한다(`calibrationMarkerIds`).

> **딕셔너리 범위를 반드시 지킬 것.** 기본값 `DICT_4X4_100`(`dictionaryId: 1`) 은 ID 가 **0~99 뿐**이다.
> 범위를 벗어난 ID 를 주면 OpenCV 는 예외 없이 빈 이미지를 돌려주므로,
> "여백만 있는 흰 사각형" 이 투사되고 원인을 찾기 어렵다.
> 그래서 기본 예약값을 뒤쪽 네 개(**96~99**)로 잡고, 시작할 때 범위를 검증해 경고한다.
> 콘텐츠 폴더 이름도 같은 범위 안이어야 하며, 이것도 시작할 때 함께 검증한다
> (→ `StoryRestApp.ValidateContentMarkers`). 콘텐츠에 쓸 수 있는 ID 는 **0~95** 다.

#### 마커 개수를 더 늘려야 한다면

| 딕셔너리 | `dictionaryId` | 마커 수 | 마커 간 최소 해밍거리 | 기존 인쇄물 |
|---|---|---|---|---|
| `DICT_4X4_50` | 0 | 50 | 4 | — |
| `DICT_4X4_100` | **1** (현재) | **100** | 3 | **그대로 유효** |
| `DICT_4X4_250` | 2 | 250 | 3 | 그대로 유효 |
| `DICT_5X5_100` | 5 | 100 | 6 | **전량 재인쇄** |

4X4 계열은 같은 바이트 표를 앞에서부터 잘라 쓴다. `DICT_4X4_100` 의 0~49번은 `DICT_4X4_50` 의 것과
**비트까지 동일**하고 오류정정 비트도 1 로 같아서, 50 → 100 확장에는 재인쇄가 필요 없다.
대신 마커 간 최소 거리가 4 → 3 으로 줄어 오검출 여유가 조금 좁아진다.
현장에서 엉뚱한 ID 가 튀면 칸 수를 늘린 `DICT_5X5_100` 으로 올린다 — 이때는 전량 재인쇄해야 한다.

### 자동 인식의 물리적 한계 — 투사면이 밝으면 안 된다

**프로젝터는 빛을 더하기만 한다.** 검은색을 쏜다는 것은 그 자리에 아무것도 쏘지 않는다는 뜻이고,
거기에는 투사면 원래 밝기가 그대로 보인다. 즉 투사면보다 어두운 영역은 만들 수 없다.

카메라가 보는 밝기 = min(255, 투사면 반사 + 투사광) 으로 계산해 보면 이렇다.

| 투사면 | 마커 흰 칸 | 마커 어두운 칸 | 대비 |
|---|---|---|---|
| 어두운 책상 (30) | 255 | 30 | **225** |
| 흰 종이 (200) | 255 | 200 | **55** |

**어두운 칸의 색을 바꿔도 나아지지 않는다.** 다른 색을 쏘면 그만큼 밝아져 대비가 오히려 준다
(흰 종이에 파란색을 쏘면 대비가 55 → 31로 떨어진다). 검은색이 이미 최적이다.

그러므로 자동 인식이 안 될 때 손댈 것은 색이 아니라 **투사면과 조명**이다.

- 캘리브레이션 동안만이라도 투사면에 어두운 천이나 매트를 깐다
- 주변 조명을 낮춘다
- 프로젝터 밝기를 최대로 올린다
- 광택 있는 면은 반사가 심하니 무광으로 바꾼다

이 조건을 맞출 수 없는 자리라면 아래 수동 방식으로 넘어간다. 설치에는 지장이 없다.

### 실패할 때 — 자리 사각형 + 실물 마커(폴백)

투사된 마커는 다음 경우 검출되지 않는다.

- 투사면이 밝아 대비가 부족할 때 (위 표 참고 — 가장 흔한 원인)
- 투사면에 무늬가 있을 때
- 프로젝터 초점이 안 맞을 때
- 광택 있는 책상에서 반사가 심할 때

이때는 수동으로 넘어간다.

1. 프로젝터가 네 귀퉁이에 **마커를 놓을 자리 사각형**을 쏜다. 지금 짚을 자리만 밝게 그린다.
2. 설치자가 그 안에 **책자 마커를 맞춰 놓는다.** 카메라가 위치를 읽는다.
3. 네 귀퉁이를 반복한다.

설치자가 이미 손에 들고 있는 마커로 잡을 수 있어 마우스나 별도 입력장치가 필요 없다.

사각형 크기는 `aruco.json`의 `manualTargetSize`(화면 짧은 변 대비 비율)로, 현장에서 `+`/`-`로 맞춘다.
실물 마커가 몇 cm 인지와 프로젝터 거리에 따라 화면상 크기가 달라지기 때문이다.
**사각형과 마커가 같은 크기여야 마커 중심이 대응점에 온다** — 대응점으로 쓰는 값이 마커 중심이므로,
크기가 어긋나면 그만큼 보정이 밀린다.

사각형은 **네 모서리만** 그린다. 마커 면 위로 투사광이 떨어지면 흑백 대비가 무너져 인식률이 떨어진다.
선 두께는 사각형을 키워도 화면상 일정하게 유지된다(`ArUcoEditMode.TargetFrame`).

카메라에 **IR 패스 필터**를 다는 구성에서는 자동 인식이 원리적으로 불가능하다 —
프로젝터는 가시광만 내므로 투사된 마커가 카메라에 도달하지 않는다.
그 구성에서는 이 수동 경로가 유일한 보정 방법이다(사각형은 사람 눈으로 보고, 카메라는 실물 마커만 읽는다).

### 공통

- 네 쌍으로 호모그래피를 푼다. `ArUcoHomography`의 닫힌 해를 그대로 쓴다.
- `aruco.json`의 해당 세트 `calibration`에 저장한다.
- **검증 단계를 둔다.** 구한 변환으로 네 귀퉁이에 다시 표식을 쏴서,
  설치자가 조준점과 실제 투사 위치가 겹치는지 눈으로 확인한다.
- 캘리브레이션이 없으면 항등 변환(= 기존 레터박스 방식)으로 동작한다. 일단 뜨긴 뜬다.

## 2. 오브젝트 구조

세트가 독립이어야 하므로(→ SPEC §2) **세트 하나 = GameObject 하나 + 그 아래 전용 인스턴스**로 만든다.
전역 싱글턴에 카메라·마커 상태를 두지 않는다.

```
[Scene]
└─ StoryRestApp                     ← 부트스트랩. 설정 읽고 나머지를 생성
   │   AppConfig   (Setting.json → floor)
   │   ArUcoConfig (aruco.json   → sets[])
   │
   ├─ Set_A                         ← ArUcoSet  (카메라 1 : 프로젝터 1)
   │  ├─ ArUcoMarkerTracker         카메라 캡처 + 마커 검출 (세트 전용 인스턴스)
   │  ├─ ArUcoContentLibrary        floor_<N>/<id>/ 스캔 + AVPro 플레이어 풀
   │  └─ ArUcoProjectionView        Camera(targetDisplay) + Canvas + 워프 UI 풀
   │
   ├─ Set_B                         ← 2·3층에서만 생성 (sets[] 길이가 결정)
   │  └─ (동일 구성)
   │
   ├─ KeywordWall_1                 ← 키워드 월 (내용 미정, 자리만 잡아둠)
   ├─ KeywordWall_2
   │
   └─ ArUcoAdjustMode               ← 편집모드. 세트를 골라 그 세트를 조정
```

### 각 컴포넌트의 책임

| 컴포넌트 | 책임 | 기존 코드 |
|---|---|---|
| `StoryRestApp` | 설정 로드, 세트 생성, 디스플레이 활성화 | **신규** |
| `ArUcoSet` | 한 세트의 tracker/library/view를 묶고 매 프레임 연결 | **신규** (`ArUcoPageOverlay` 분해) |
| `ArUcoMarkerTracker` | 캡처 + 검출 + 꼭짓점 스무딩 | **수정** (세트별 인스턴스화, 스레드화) |
| `ArUcoContentLibrary` | 마커 ID → 영상. AVPro 플레이어 풀 | **신규** (`ArUcoImageLibrary` 대체) |
| `ArUcoProjectionView` | `H_camproj` 적용 + 워프 메시 배치 + 디스플레이 출력 | **신규** (`ArUcoPageOverlay` 분해) |
| `ArUcoHomography` | 4점 → 사영변환 | **그대로** |
| `ArUcoWarpedImage` | 비사각형 텍스처 렌더 | **소폭 수정** (`Texture2D` → `Texture`) |
| `ArUcoAdjustMode` | 편집모드 | **수정** (세트 선택 + 코너 보정 추가) |
| `ArUcoConfigStore` | 설정 입출력 | **수정** (세트 구조) |

`ArUcoPageOverlay`가 지금 혼자 하고 있는 일(설정 로드 · UI 구성 · 좌표 계산 · 풀 관리)을
위 셋으로 나눈다. 세트가 여럿이 되면 한 클래스가 다 들고 있을 수 없다.

## 3. 디스플레이 출력

**`ScreenSpaceOverlay`를 버리고 `ScreenSpaceCamera` + 세트별 `Camera`를 쓴다.**

이유:

- Overlay 캔버스는 `Screen.width/height`에 묶인다. 기존 `FitFrameToScreen()`이 그 값을 쓰는데,
  멀티 디스플레이에서 `Screen.*`는 **주 디스플레이 기준**이라 세트 B의 좌표가 어긋난다.
- 디스플레이별 출력은 `Camera.targetDisplay`가 정공법이다.
  각 세트의 카메라에 `targetDisplay`를 지정하고, 캔버스를 그 카메라에 붙인다.

```csharp
// 세트마다
var cam = new GameObject($"Cam_{set.name}").AddComponent<Camera>();
cam.targetDisplay = set.displayIndex;
cam.clearFlags = CameraClearFlags.SolidColor;
cam.backgroundColor = Color.black;      // 투사면에는 검은색 = 빛 없음
cam.orthographic = true;

canvas.renderMode = RenderMode.ScreenSpaceCamera;
canvas.worldCamera = cam;
canvas.planeDistance = 1f;
```

- 출력 해상도는 `Display.displays[i].renderingWidth/Height`로 읽는다. `Screen.*`를 쓰지 않는다.
- 빌드 시작 시 `Display.displays[i].Activate()`를 사용 중인 인덱스만큼 호출한다.
- **에디터에서는 디스플레이가 1개뿐이다.** 개발 중에는 `sets[]`를 1개로 줄이거나
  디버그용 "한 화면에 나눠 그리기" 모드로 확인한다(→ §7).

### UI는 uGUI로 고정한다

화면 구성은 **uGUI(Canvas 기반)** 만 쓴다. UI Toolkit(UIElements)은 쓰지 않는다.

- 마커 위에 눕히는 콘텐츠는 `ArUcoWarpedImage`(= `UnityEngine.UI.Graphic` 상속)로 그린다.
  임의의 사각형으로 메시를 직접 만들어야 하는데, 이건 uGUI 의 `OnPopulateMesh` 로만 가능하다.
- 텍스트는 **TextMeshPro** 로 통일한다. 기존 프로젝트 UI(`SerialPortLogPanel` 등)가 이미 `TMP_Text` 를 쓴다.
- 한글은 **TMP Settings 의 fallback 에 등록한 `NotoSansKR-Regular SDF`** 가 채운다.
  런타임에 만드는 UI 도 폰트를 따로 지정할 필요가 없고, 전시 PC 에 어떤 OS 폰트가 깔려 있든 결과가 같다.
  (legacy `Text` + `Font.CreateDynamicFontFromOSFont` 방식은 쓰지 않는다 — 설치 환경에 의존한다.)

### 카메라 영상은 투사하지 않는다

배경은 항상 검은색이고 콘텐츠만 그린다. 카메라 프리뷰는 **점검용 스위치**(`sets[].showCameraPreview`)로만 켜진다.
`C`로 토글하며 **편집모드 안팎 어디서든 받는다.** 값이 파일에 남으므로 편집모드를 나가도 유지된다 —
인쇄한 마커가 실제로 잡히는지, 초점과 조명이 충분한지는 전시 상태 그대로 두고 보는 편이 빠르기 때문이다.
편집모드 밖에서는 세트를 고르는 개념이 없으므로 **모든 세트가 한 번에** 켜지고 꺼진다.
켜 두면 시작 로그에 경고가 남고 편집모드 HUD에도 표시된다. 전시 중에는 반드시 끈다.

프리뷰는 화면 전체에 반투명으로 깐다(워프하지 않는다). 카메라와 프로젝터는 화각이 다르므로
이 화면은 정합 확인용이 아니라 **"카메라가 무엇을 보고 있는지"** 를 보는 용도다.
정합은 코너 보정(§1)과 마커 배치로 맞춘다.

이 결정 덕에 평상시 `OpenCVMatUtils.MatToTexture2D` 호출이 사라진다(매 프레임 전체 프레임 GPU 업로드).
층당 PC 1대 구성에서 가장 크게 절약되는 지점이다.

## 4. 설정 파일

### `Setting.json` — 앱 전역

```json
{ "floor": 1 }
```

### `aruco.json` — ArUco 관련 전부

```json
{
  "dictionaryId": 1,
  "smoothing": 0.4,
  "holdSeconds": 0.3,
  "warpSubdivisions": 10,
  "perspectiveMapping": true,
  "maxSimultaneous": 0,
  "calibrationMarkerIds": [96, 97, 98, 99],

  "sets": [
    {
      "name": "A",
      "displayIndex": 1,
      "camera": { "deviceId": 0, "backend": 0, "width": 1280, "height": 720, "fps": 30 },
      "showCameraPreview": false,

      "calibration": {
        "projectorPoints": [[0.15,0.15],[0.85,0.15],[0.85,0.85],[0.15,0.85]],
        "cameraPoints":    [[210,140],[1030,150],[1040,600],[205,595]],
        "valid": true
      },

      "globalScale": 1.0,
      "globalOffsetX": 0.0,
      "globalOffsetY": 1.2,
      "markers": [
        { "id": 3, "scale": 1.2, "offsetX": 0.10, "offsetY": -0.40, "rotationOffset": 0, "enabled": true }
      ]
    }
  ]
}
```

- `projectorPoints`는 **출력 해상도에 대한 0~1 정규화 좌표**다. 프로젝터 해상도가 바뀌어도 유지된다.
- `cameraPoints`는 카메라 픽셀 좌표. 캘리브레이션으로 채워진다.
- `showCameraPreview`는 점검용이다(→ §3). 세트마다 카메라가 다르므로 값도 세트에 둔다. 전시 중에는 `false`.
- `globalScale`과 `markers`가 **세트 안으로 들어간 것**이 기존 구조와의 핵심 차이다.
- **최종 배치 = 세트 공통값 + 마커별 값**이다.
  `globalOffsetX/Y`는 모든 마커에 더해지고 `globalScale`은 곱해진다.
  위 예에서 3번 마커는 `(0.10, -0.40 + 1.2)` = `(0.10, 0.80)` 자리에 뜬다.
  "콘텐츠는 늘 마커 위쪽" 같은 공통 배치를 한 번에 잡고 예외만 개별로 손보라는 값이다.
  마커별 값을 일일이 고치지 않으므로 나중에 전체를 다시 밀 수 있다.
- 층이 다르면 콘텐츠 폴더가 다르므로, 층마다 별도의 `aruco.json`을 갖는 셈이 된다.

`JsonUtility`는 중첩 리스트와 `Vector2[]`를 다루므로 좌표는 `[{x,y}]` 형태의
`[Serializable]` 구조체 배열로 둔다(`float[][]`는 직렬화되지 않는다).

## 5. 콘텐츠 — AVPro Video

### 탐색

```
StreamingAssets/floor_<N>/<마커ID>/<아무이름>.mp4
```

- 시작 시 `floor_<N>/` 하위 디렉터리를 훑어 이름이 정수인 것만 마커 ID로 등록한다.
- 각 폴더에서 영상 확장자 파일 1개를 고른다. 여러 개면 첫 번째 + 경고(→ SPEC §4).
- 편집모드 `F5`로 재스캔한다(현장에서 파일 교체 후 재실행 불필요).

### 플레이어 풀

마커마다 `MediaPlayer`를 상시 열어두면 안 된다. 디코딩 비용이 마커 수에 비례한다.

```
ArUcoContentLibrary
  ├─ 등록된 마커 ID → 파일 경로   (스캔 결과, 가벼움)
  └─ MediaPlayer 풀 (크기 = maxConcurrentVideos)
       마커가 보이면 빌려주고, 사라지면 일정 시간 뒤 반납
```

- 풀 크기는 설정값. 기본은 세트당 4 정도로 두고 현장에서 조정한다.
- 반납 시 `Stop()`. 재대여 시 `OpenMedia` + 처음부터 재생(→ SPEC §8 미확정 2의 가정).
- 오디오는 쓰지 않으므로 `AudioOutput`을 비활성화하고 볼륨 0으로 연다.
- AVPro 텍스처는 플랫폼에 따라 **상하 반전**될 수 있다.
  `TextureProducer.RequiresVerticalFlip()`을 읽어 UV의 v를 뒤집는다.
  → `ArUcoWarpedImage`에 `flipV` 플래그를 둔다.

### 렌더 경로

`ArUcoWarpedImage.mainTexture`를 `Texture`로 올려 AVPro 텍스처를 그대로 물린다.
메시 생성 로직은 기존 것을 쓴다.

**Windows 백엔드는 `RequiresVerticalFlip()`이 항상 true 다.** 실측으로 확인했다.
`ArUcoWarpedImage.FlipV`로 UV 를 뒤집지 않으면 모든 영상이 상하 반전되어 나온다.

### 카메라 없이 콘텐츠 점검하기

`aruco.json`의 `debugPreviewContent`를 켜면 마커 인식과 무관하게
등록된 콘텐츠를 화면에 격자로 늘어놓는다. 카메라가 없는 자리에서 영상 파일과
재생 경로만 빠르게 확인할 때 쓴다. **전시 중에는 반드시 꺼 둔다**(화면에 경고 문구가 뜬다).

## 6. 스레딩과 성능

층당 PC 1대가 최대 **4화면 + 카메라 2 + 영상 여러 개**를 감당해야 한다(→ SPEC §2).

### 캡처·검출을 워커 스레드로

현재 `ArUcoMarkerTracker.Update()`는 메인 스레드에서 `grab()` / `retrieve()` / `detectMarkers()`를
모두 돌린다. `grab()`은 **블로킹**이다. 카메라 2대면 매 프레임 두 번 막힌다.

```
[워커 스레드 / 세트마다 1개]
  grab → retrieve → cvtColor → detectMarkers
  결과(네 꼭짓점 + ID)를 잠금으로 보호된 버퍼에 쓴다

[메인 스레드]
  버퍼를 읽어 스무딩 → 배치 → 렌더
  (편집모드일 때만) 프레임을 Texture2D로 업로드
```

- OpenCV `Mat` 연산은 Unity API가 아니므로 워커에서 안전하다.
  `Texture2D` 업로드만 메인 스레드에서 한다.
- 스무딩은 메인 스레드에 남긴다. `Time.deltaTime` 기반이고 렌더 주기와 맞아야 한다.
- 검출 해상도는 표시 해상도와 무관하다. 720p로 충분하며, 필요하면 더 낮춘다.

### 그 밖에

- 안 보이는 마커의 `MediaPlayer`는 정지 → 디코딩 부하 제거.
- 평상시 카메라 프레임을 텍스처로 올리지 않음(→ §3).
- `warpSubdivisions`는 마커당 (n+1)² 정점이다. 10이면 121개 — 문제없지만 무한정 올리지 않는다.

## 7. 편집모드

기존 `ArUcoAdjustMode`를 확장한다. 조작 체계(반복 입력, Shift 미세조정, 자동 저장)는 그대로 쓴다.

### 조작 (`ArUcoEditMode`)

| 키 | 기능 |
|---|---|
| `F1` | 편집모드 진입/종료 |
| `F2` | 단계 전환 (마커 배치 ↔ 코너 보정) |
| `1`~`9` | 조정할 세트 선택 (세트가 여럿일 때) |
| `Tab` / `Shift+Tab` | 마커 선택 |
| `← → ↑ ↓` `+` `-` `[` `]` | 선택한 마커의 위치 · 크기 · 회전 |
| `Ctrl` 병행 | 세트 전체 위치 · 크기 (`globalOffsetX/Y`, `globalScale`) |
| `PageUp` / `PageDown` | 세트 전체 배율 |
| `Space` | 코너 보정 진행 (자동 시작 → 수동 전환 → 점 확정 → 완료) |
| `+` `-` (수동 보정 중) | 마커 놓을 자리 사각형 크기 (`manualTargetSize`) |
| `Backspace` | 마커 초기화 / 보정값 지우기 |
| `C` `V` `D` `P` `F5` | 카메라영상 · 콘텐츠 표시 · 마커테두리 · 원근 · 콘텐츠 다시읽기 |
| `Enter` | 즉시 저장 |
| `Shift` 병행 | 미세조정 |

- HUD는 **선택한 세트의 화면에만** 뜬다. 다른 프로젝터는 전시 상태를 유지한다.
- **콘텐츠 표시는 단계마다 기본값이 다르다** — 마커 배치는 보이고, 코너 보정은 숨긴다(조준점을 가리므로).
  `V`로 그 자리에서 뒤집을 수 있고, 단계를 바꾸면 기본값으로 돌아간다.
  보정 중에도 콘텐츠를 띄워 두면 조준점과 실제 투사 위치를 함께 볼 수 있다.
- **카메라영상(`C`)만 편집모드 밖에서도 받고, 나가도 유지된다.** 설정에 남는 값이기 때문이다(→ §3).
  밖에서 누르면 모든 세트가 함께 토글되고, 안에서 누르면 선택한 세트만 바뀐다.
  나머지 편집 상태(하이라이트·콘텐츠 숨김·마커 테두리)는 나갈 때 전부 전시 상태로 되돌린다.
- 편집모드 밖에서 값을 바꾸는 키는 받지 않는다(→ SPEC §6). `C`는 표시 스위치라 예외로 둔다.
- 코너 보정 중에는 **HUD를 화면 가운데로 옮긴다.** 좌상단에 두면 그쪽 조준점을 가린다.
- 저장은 **1.5초 무입력 시 자동 + `Enter` 즉시**. 전시장 PC는 예고 없이 꺼진다.
- 평상시에는 어떤 편집 UI도 보이지 않는다(→ SPEC §6). 편집 UI는 처음 필요할 때 만든다.
- `Esc`는 기존 `SettingsPanelUI`가, `S`/`E`는 `GameManager`가 쓰므로 피했다.

### 에디터 개발용

빌드에서는 세트마다 `sets[].displayIndex`가 가리키는 디스플레이로 그대로 나간다.
에디터에서도 **Game 뷰 상단의 Display 드롭다운**으로 세트별 화면을 실제 비율 그대로 볼 수 있고,
Game 뷰를 두 개 띄우면 동시에 볼 수도 있다. (`Display.Activate()`는 빌드에서만 필요하다.)

`aruco.json`의 `editorPreview`를 켜면 에디터에서만 세트들을 한 화면에 좌우로 나눠 그린다.
**기본은 꺼져 있다** — 나눠 그리면 세트 하나의 화면 비율이 실제 프로젝터와 달라져
(1920×1080 → 960×1080) 정합을 눈으로 맞추는 §1 캘리브레이션에서 감각이 어긋나기 때문이다.
두 세트를 한눈에 훑어보고 싶을 때만 임시로 켠다.

### 코드는 어디에 두는가

기본 어셈블리는 모든 asmdef 어셈블리를 자동 참조하므로
**OpenCV·AVPro·ArUcoPages 참조를 따로 설정할 필요가 없다.**
(패키지 쪽에서 AVPro를 쓰려 했다면 `ArUcoPages.asmdef`에 참조를 추가해야 했지만, 그럴 일이 없어졌다.)

네임스페이스는 `StoryRest` / `StoryRest.ArUco`를 쓴다.
기존 패키지 타입은 전역 네임스페이스에 `ArUco` 접두어로 있어 이름이 충돌하지 않는다.

`ArUcoPages`는 다른 프로젝트에도 쓰는 범용 패키지였지만,
이번 변경(세트·프로젝터 캘리브레이션·AVPro)은 이 전시 전용이다.
**패키지를 범용으로 유지하려 애쓰지 않고 이 프로젝트에 맞게 고친다.**
범용 버전이 필요하면 `Assets/ArUcoPages/`의 현재 상태가 이미 `.unitypackage`로 남아 있다.

## 10. 키워드 월

벽면 프로젝터 2대에 과학 낱말이 떠다니는 배경 화면. 관람객 인터랙션은 없다.

- 낱말 목록: **`floor_<N>/keywords.txt`** — 한 줄에 하나, `#`로 시작하면 주석.
  콘텐츠와 같은 층 폴더에 두어 층마다 다른 낱말을 쓸 수 있다. 메모장으로 고칠 수 있게 평문이다.
- 동작 설정: **`keywordwall.json`** — 디스플레이 번호, 개수, 크기·속도·투명도 범위, 색상.
- 좌표는 화면을 0~1로 보는 정규화 값이라 프로젝터 해상도가 달라도 같은 그림이 나온다.
- 시간은 `unscaledDeltaTime`을 쓴다. `GameManager`가 `Time.timeScale`을 만지므로
  배경 화면이 거기 끌려가면 안 된다.

### 다섯 가지 움직임

| 패턴 | 움직임 |
|---|---|
| `Drift` | 직선으로 흐르다 가장자리에서 튕긴다 |
| `Wave` | 가로로 흐르며 위아래로 물결친다 |
| `Orbit` | 한 점을 중심으로 타원을 그린다 |
| `Bob` | 제자리에서 천천히 흔들린다 |
| `Zigzag` | 대각선으로 가다 주기적으로 꺾인다 |

낱말마다 패턴·크기·색·투명도·수명을 무작위로 배정해 같은 그림이 반복되지 않게 한다.
수명이 끝나면 서서히 사라지고 다른 낱말이 등장한다.

### 겹침 처리 — 이 화면에서 가장 중요한 부분

낱말이 뭉치면 글자가 겹쳐 아무것도 읽을 수 없다. 실제로 처음 구현했을 때 화면 한쪽에
여섯 개가 포개져 판독이 불가능했다. 두 가지로 막는다.

1. **등장 위치 선택** — 이미 떠 있는 낱말들과 가장 덜 붙는 자리를 골라 태어난다.
2. **서로 밀어내기** — 글자 상자를 타원으로 보고 겹친 만큼만 부드럽게 밀어낸다.
   궤도를 도는 낱말은 중심까지 함께 옮겨야 다음 프레임에 제자리로 돌아가지 않는다.

가장자리 여백(`edgeMargin`)은 설정으로 뺐다. 프로젝터 렌즈 왜곡이나 투사면 모서리 상황이
설치마다 달라 현장에서 조정해야 한다.

### 검증 기록 (1~3단계)

- 호모그래피: 대응점 4쌍을 사다리꼴로 두고 왕복 매핑 오차 **1.3e-7** 확인.
- 세트 2개 구성 시 뷰포트가 좌우로 분할되고 캔버스 크기가 각각 960×1080으로 잡히며,
  두 세트가 서로의 캔버스를 렌더하지 않음(카메라를 Y축으로 10000씩 분리).
- 카메라 미연결 시 검은 화면에 세트별 안내 문구가 뜨고, 설정 검증이
  "디스플레이가 부족하다"를 정확히 보고함.

### 검증 기록 (5단계)

- 서로 다른 종횡비의 mp4 3개를 동시 재생. 슬롯 4개 중 3개 사용, 1개 유휴 —
  풀이 의도대로 동작함.
- 모든 슬롯이 `looping=true`, `muted=true`, 재생 위치가 진행 중임을 확인.
- Windows 백엔드의 `RequiresVerticalFlip()`이 true 인데 화면이 똑바로 나옴
  → `FlipV` 처리가 실제로 먹고 있다는 증거.

### 검증 기록 (4·6단계) — 카메라 없이 확인한 범위

화면에 투사한 마커를 카메라로 렌더링해 되읽는 방식으로, 장비 없이 파이프라인 전체를 확인했다.

| 확인 항목 | 결과 |
|---|---|
| 마커 텍스처 생성 | 46~49 모두 자기 ID 로 재검출됨 (좌우 반전 없음) |
| 딕셔너리 범위 밖 ID | `null` 로 거부되고 에러 로그 |
| 투사 위치 정확도 | 검출 좌표를 정규화하니 `projectorPoints` 와 정확히 일치 |
| ID ↔ 코너 대응 | 46→(0.15,0.15) 47→(0.85,0.15) 48→(0.85,0.85) 49→(0.15,0.85) |
| 자동 인식 흐름 | 30프레임 수집 후 실패 판정 → 수동 전환 안내 |

당시 예약 ID 는 `DICT_4X4_50` 기준의 46~49 였다. 지금은 `DICT_4X4_100` 의 **96~99** 를 쓰며,
ID 만 바뀌었을 뿐 코너 대응 순서(좌상 → 우상 → 우하 → 좌하)와 로직은 그대로다.

**남은 것은 실제 카메라·프로젝터로 정합을 확인하는 일뿐이다.**
위 결과의 "카메라 좌표" 자리에 실제 카메라 픽셀이 들어올 뿐 로직은 동일하다.

1~3은 서로 얽혀 있어 한 덩어리로 보는 편이 낫다.
4는 단독으로 가장 중요하고, 실패하면 나머지가 다 어긋나므로 실물 프로젝터로 확인해야 한다.
